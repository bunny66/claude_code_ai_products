You are a senior staff engineer doing a deep architectural audit of the microservice in the current working directory, for the purpose of writing context documentation that a future Claude Code session (with zero prior context) can rely on to produce correct, non-guessing output.

Target: $ARGUMENTS (default: `full` — run every phase)

## Working method
Don't read every file. Use glob/grep to confirm a pattern holds codebase-wide, then read 2-3 representative examples per pattern rather than every instance (e.g., 2-3 controllers to confirm the module style, not all 40). Exhaustive reading on a real ~100-file service will blow the context budget before you've written a single file.

## Resumability
A large service can genuinely take longer than one session. This command must survive being interrupted — context limit, closed terminal, network drop — and pick back up without redoing finished work.

- **Write as you go, not at the end.** Each phase below writes its own file the moment that phase finishes exploring — never hold everything in memory for a final dump. Whatever's already written stays written if the run stops.
- **Provenance stamp on every file:** `> Generated by /study-service on <date> at commit <short sha>.` (sha from `git rev-parse --short HEAD`). This is what staleness checks and resume validation both key off. Because of the Phase 0 git guard, this sha is always on the repository's detected default branch — never a dirty or branch-local state — so it is comparable across the team.
- **Track progress in `.claude/context/_progress.md`** — plain markdown, committed like everything else. After finishing a phase, mark it `done` (with commit sha) or `not-applicable` (with a one-line reason, e.g. "worker service, no exposed endpoints") in this file, and mark the next phase `in-progress` before you start it. If a phase stops on an unanswered ambiguity question, it stays `in-progress` — it is not `done` until its file is actually written.
- **On a `full` run, Phase 0 reads `_progress.md` first.** An incomplete run resumes from the first `pending`/`in-progress` phase — announce that plainly ("Resuming — phases 0-3 already done, continuing from Phase 4") rather than asking permission. Continuing prior work doesn't need a gate; starting over would.
- A scoped argument (e.g. `/study-service api`) ignores `_progress.md` entirely — that's an explicit one-phase override, not a resume.

## Non-negotiable: Ambiguity Protocol

You will find things the code cannot answer for you: intent behind a business rule, whether a dependency is hard or best-effort, who owns a module, whether a field is PII, whether an undocumented pattern is deliberate or drift.

**When that happens: stop the current phase immediately. Do not guess. Do not proceed and note it as a caveat "to be safe." Ask.**

Rules for asking well:
- Only stop for things that would change the *content* of the context docs — not style nits (indentation, naming casing, etc.). If you can verify it from code/tests/git history/commit messages, **or from existing README/docs/ADR/CHANGELOG files**, don't ask — read those first, don't make the user re-answer something already written down.
- Batch ambiguities found within the *same phase* into one question block — don't interrupt the user once per finding.
- Format the block clearly:

  ```
  ### ❓ Need input before continuing — Phase N (name)
  1. [specific, answerable question]
  2. [specific, answerable question]

  Reply with answers, or say "skip" to have me record these as open assumptions in the docs and continue.
  ```
- Honor "skip": write the item into the relevant file under an `## Open Questions / Assumptions` section instead of inventing an answer.
- Never write a business-logic explanation, ownership claim, or compliance classification you inferred but didn't verify — flag it instead.
- For every non-obvious claim in `business-logic.md` and `dependencies.md`, cite the file path (and line, if it helps) it's drawn from. An unauditable claim is exactly what this protocol exists to prevent — a claim with no citation is no more trustworthy than a guess.

## Phase 0 — Pre-flight

### Git state guard (runs first, no exceptions — applies even to scoped, single-phase invocations)
1. Detect the default branch from `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` (remove the `origin/` prefix). If unavailable, inspect repository metadata and remote branches; if the default branch remains ambiguous, ask the developer and stop until confirmed.
2. Check the current branch: `git rev-parse --abbrev-ref HEAD`. If it is not the detected default branch, **exit immediately** and name both branches. Do nothing else — no exploration, no file writes, no `_progress.md` read.
3. Check the working tree is clean: `git status --porcelain`. Any output at all (staged, unstaged, or untracked)? **Exit immediately** and ask the developer to commit or stash changes. This runs before pulling to avoid conflicts.
4. Sync with origin: `git fetch origin [default-branch]`, then `git pull origin [default-branch] --ff-only`. If fetch/pull fails, exit with the underlying git error. If fast-forward fails, ask the developer to reconcile manually; do not resolve divergence automatically.
5. Confirm alignment: `git rev-parse HEAD` must equal `git rev-parse origin/[default-branch]`. Any mismatch — **exit** rather than guessing why.

Only once all five git checks pass does the rest of Phase 0 run:

6. Confirm this looks like a single project-component root (for example `pyproject.toml`, `requirements.txt`, `environment.yml`, `package.json`, `pom.xml`, `go.mod`, `dvc.yaml`, or `MLproject` at top level), not a monorepo with multiple independently-deployable components. If it looks like a monorepo, stop and ask which component directory to scope to.
7. Check `.claude/context/_progress.md`:
   - **Missing, and no other `.claude/context/*.md` files exist:** fresh service. Create `_progress.md`, proceed to stack detection then Phase 1.
   - **Present and marked all-done** (or missing but a full set of content files + `CLAUDE.md` already exist — pre-dates this convention): this is a *completed* prior study, not a resume. Read the commit sha from each file's provenance stamp, run `git diff --stat <stamped_sha>..HEAD` to see what's changed since, and **stop and ask** whether to do a full re-study, an incremental update scoped to the stale files, or a targeted refresh of one file.
   - **Present and NOT marked all-done:** an interrupted run. Validate each phase marked `done` — its file must exist and not look truncated, and its stamped commit must still cover the relevant paths (diff against HEAD); demote to `pending` if stale or missing. Resume from the first `pending`/`in-progress` phase and say so plainly — don't ask permission to continue prior work.
   - `--refresh` passed: skip all of the above, wipe `.claude/context/`, start clean.
8. Detect stack and workload from project manifests and code: Python environment files, notebooks, ML frameworks, training/evaluation/inference entry points, data orchestration/configuration, model registries, APIs, Docker/Kubernetes manifests, and CI. Use evidence to tailor phases and mark clearly non-applicable phases in `_progress.md` rather than leaving them pending.

## Phase 1 — Structural inventory & pattern recognition
Map directory structure, entry point(s), and where config/env is loaded from. Note build and deploy mechanics (Dockerfile stages, k8s deployment/configmap — **names and purpose only, never secret values**).

Then classify and *name* the organizational pattern actually in use, and produce a concrete module/file distribution map — not a directory listing, but "this folder = this responsibility," so a future session knows exactly where new code belongs instead of guessing by analogy.

- **Data and ML projects**: map ingestion, validation, transformation, feature generation, training, evaluation, batch inference, and serving stages where present. Identify how configuration, datasets, model artifacts, and versions flow between them.
- **Application/API components**: map the actual route/module organization, request-to-storage or request-to-model path, and where shared concerns such as validation, authorization, and error handling attach.
- **Hybrid components**: document how interfaces, pipelines, jobs, and downstream components fit together; distinguish local responsibilities from delegated work.

Ambiguity trigger: if patterns are mixed in a way that isn't an obvious old-vs-new migration (no clear date/version boundary explaining the split), ask which pattern is the intended direction. This isn't cosmetic — it determines which convention *new* code should follow, not just how existing code gets documented.

→ Write `overview.md` now, including the pattern name and distribution map. Mark this phase `done` in `_progress.md` before moving on.

## Phase 2 — Interfaces and API surface
Enumerate exposed interfaces that apply: API endpoints/routes/resolvers (method, path, purpose, request/response shape, validation, auth); CLI commands; scheduled jobs; pipeline entry points; event consumers/producers; and batch or online inference interfaces. Enumerate outbound calls and SDK integrations, including data stores, registries, artifact stores, and external services. Record configuration source by variable or settings name, never its secret value, and note failure behavior.
Ambiguity trigger: an endpoint or outbound call whose purpose isn't recoverable from code, tests, or comments.
Known limitation to record, not solve: a single service's repo usually can't tell you who consumes its API. Write a standing note in `api-surface.md` under Open Questions that consumers are unknown from this repo alone — check a service registry, API gateway config, or ask directly before treating any endpoint as safe to change freely.

→ Write `api-surface.md` now. If this component exposes no API, CLI, job, pipeline, event, or inference interface, mark this phase `not-applicable` in `_progress.md` with that reason and skip the file entirely. Otherwise mark `done`.

## Phase 3 — Data, model & storage
Document database schemas and migrations, dataset locations/formats/versions, feature definitions, data contracts, model inputs/outputs/signatures, artifact formats, registry/storage integrations, and relevant cache patterns. Record lineage and ownership only when verified. Flag fields or data sources that may contain sensitive information as `sensitive: likely` or `sensitive: confirm` — do not assume masking or access policy.
Ambiguity trigger: a field or dataset's sensitivity classification, or an unexplained schema/feature quirk (e.g., duplicated field across stores) with no code, documentation, or migration note explaining it.

→ Write `data-model.md` now. Mark `done` in `_progress.md` (or `not-applicable` with reason, e.g. a stateless proxy service with no storage of its own).

## Phase 4 — Cross-service dependencies & messaging
Search for component-to-component calls, events/queues, shared databases and data platforms, feature stores, model registries, and artifact stores. For each dependency, capture its direction, version/ownership boundary, and failure behavior (retry, dead-letter, fallback, or silent drop).
Ambiguity trigger: any dependency where criticality or failure behavior isn't evident from code.

→ Write `dependencies.md` now. Mark `done` in `_progress.md`.

## Phase 5 — Business logic & domain rules
Identify core workflows and state transitions, including data transformations, training/evaluation choices, inference behavior, and the *why* behind non-obvious rules or thresholds. Code tells you what happens, but rarely why. Never infer model validity or business intent from implementation alone.
Ambiguity trigger: any rule where you're inferring intent rather than reading it.

→ Write `business-logic.md` now. Mark `done` in `_progress.md`. (Phase 6 will reopen this file later to add test-coverage notes — that's expected.)

## Phase 6 — Operational context
Logging setup, metrics/observability, alerting, compute/runtime requirements, experiment tracking, artifact lineage, data/model quality or drift monitoring, test/evaluation coverage, and existing tech-debt markers (TODO/FIXME, skipped tests, deprecated-but-live code paths).
Cross-reference against Phase 5: for each business rule documented there, note in `business-logic.md` whether it appears to have direct test coverage. A rule with no test isn't an ambiguity to stop for — it's a fact worth recording so future changes to that rule know there's no safety net.

→ Write `operations.md` now. Re-open `business-logic.md` (already on disk from Phase 5) to append the test-coverage notes, and update its provenance stamp since it changed after that phase closed. Mark this phase `done` in `_progress.md`.

## Phase 7 — Conventions & patterns
Document the *actual* conventions in use: error handling, API/data/model contracts, validation, configuration, naming, and folder structure. Note inconsistencies as facts, not verdicts about which style is "correct" unless you can confirm one is deprecated.

→ Write `conventions.md` now, including a "where does new work go" placement guide for relevant code, data, model, test, and pipeline changes — pull the observed pattern from `overview.md`, already written in Phase 1, rather than re-deriving it. Mark `done` in `_progress.md`.

## Phase 8 — Utils / Common / Shared modules inventory
Purpose: catalog what's already built for reuse, so future work extends it instead of writing a fourth version of the same helper.

Scan common utility/shared-code locations and project-specific equivalents such as data transforms, feature definitions, model wrappers, evaluation helpers, pipeline components, reusable schemas, and artifact/version utilities. Also inventory cross-cutting interfaces, validation, exceptions, constants, and repeated helper logic wherever they actually live.

For each item: name, file path, one-line purpose, and the trigger condition — "reach for this instead of writing X."

Actively look for near-duplicate logic (the same capability implemented more than once, slightly differently — e.g. two retry wrappers with different backoff behavior). List these under a `## Consolidation Candidates` section rather than picking one as canonical yourself — merging them is a call for a human who knows the call sites, not something to resolve silently.

Check project manifests and environment files for internal/shared packages or workspace libraries. If this component imports one, list it separately as "external shared — see that project's own docs, don't re-inventory here" rather than concluding it has no shared utilities because its local common folder is thin.

Ambiguity trigger: a broadly-reused utility whose exact contract isn't clear from its signature, docstring, or tests (e.g. an untested rounding/currency helper). Anything meant for reuse needs correct semantics, not inferred ones — ask rather than guess here.

→ Write `reusable-utils.md` now, including Consolidation Candidates. Mark `done` in `_progress.md`.

## Phase 9 — Compose CLAUDE.md index

By now every applicable phase has already written its own file. This phase doesn't discover anything new — it composes the lean root `CLAUDE.md`:
- 2–3 sentence service summary
- A table: file name → one-line "load this when you're doing X" guidance, built from whatever files actually exist (skip rows for phases marked `not-applicable`). The `reusable-utils.md` row should say explicitly "load before writing any new helper, decorator, guard, or shared logic — check this first."
- **Do not use `@`-import syntax to auto-pull the context files in** — the point is these load on demand, not on every session, so CLAUDE.md stays cheap
- One line at the top: "Before working on this service, read the relevant file(s) in `.claude/context/` for the task at hand — in particular, check `reusable-utils.md` before writing any new utility, decorator, or shared logic."

Mark `_progress.md` fully complete once `CLAUDE.md` is written. Everything under `.claude/` — including `_progress.md` — is meant to be committed to the repo and shared with the team, not personal scratch; if `.claude/` appears in `.gitignore`, flag it rather than silently leaving the docs unshared.

## Phase 10 — Final report
Give the user a short summary: files written/updated, any sections marked with open assumptions, and one honest note on where confidence is lowest (e.g., "business-logic.md is thin — the payment-retry logic needs a human to confirm intent"). If this run resumed a prior interrupted session, say so plainly: which phases were reused as-is vs. redone, and why (stale vs. missing vs. never started).

## Hard constraints throughout
- Never write actual secret values, connection strings, tokens, or credentials into any context file — reference env var *names* and purpose only.
- Never state a business-logic rationale, ownership, or PII/compliance classification as fact unless it's verifiable from code/docs/tests — otherwise it's a flagged assumption or a question, not a statement.
- Never mark a phase `done` in `_progress.md` before its file is actually written and complete. A phase paused on an unanswered ambiguity question is `in-progress`, full stop — marking it `done` early is what would make resumability silently lie to the next run.
